3. Migration SQL — 001_initial_schema.sql

Tables créées :

  • profiles : id (référence auth.users), email, téléphone, public_id, rôle, is_active, timestamps
  • user_roles : attribution rôle ↔ utilisateur (unique user_id + role)
  • role_permissions : permissions par rôle
  • audit_logs : journaux d'audit immuables

Index créés sur profiles(email), profiles(role), profiles(public_id), user_roles(user_id), user_roles(role), role_permissions(role), audit_logs(user_id), audit_logs(created_at), audit_logs(action).

Trigger handle_new_user() : création automatique du profil après inscription Supabase Auth (SECURITY DEFINER).

Trigger update_updated_at_column() : mise à jour automatique de updated_at sur profiles.

CREATE EXTENSION IF NOT EXISTS pgcrypto;
CREATE TABLE profiles (...)
ALTER TABLE profiles ENABLE ROW LEVEL SECURITY;
CREATE POLICY "Les utilisateurs lisent leur propre profil" ON profiles FOR SELECT TO authenticated USING (auth.uid() = id);
...

4. Politiques RLS (activées sur toutes les tables)

TablePolitiqueTypeCondition

profilesLes administrateurs lisent tous les profilsSELECTEXISTS (user_roles WHERE role IN ('super_admin','admin'))
profilesLes utilisateurs mettent à jour leur propre profilUPDATEauth.uid() = id
user_rolesLes utilisateurs lisent leurs propres rôlesSELECTauth.uid() = user_id
user_rolesLes administrateurs lisent tous les rôlesSELECTEXISTS (admin/super_admin)
role_permissionsLecture par tous les authentifiésSELECTtrue
audit_logsLes administrateurs lisent les journauxSELECTEXISTS (admin/super_admin)

Restrictions côté client : aucun INSERT/UPDATE/DELETE direct sur user_roles, role_permissions, audit_logs depuis le navigateur. La gestion des rôles est réservée au serveur.

7. Limites identifiées

8. Prochaines étapes (Phase 2 — Transactions)

Une fois cette phase approuvée, le développement poursuivra avec :

  1. Bookmakers : 1xBet, MelBet, 1Win (logos, paramètres, pas d'intégration API simulée)
  2. Dépôts : formulaire avec choix bookmaker, montant, moyen de paiement, numéro Mobile Money, récapitulatif
  3. Retraits : formulaire avec bookmaker, montant, numéro, opérateur
  4. Numéros enregistrés : proposition d'enregistrement, CRUD des numéros Mobile Money
  5. Références de transaction : génération unique côté serveur
  6. Statuts : en attente, en cours, action utilisateur requise, validée, rejetée, annulée
  7. Migrations SQL : transactions, payment_methods, user_saved_numbers, bookmakers, payment_providers, payment_instructions
  8. RLS : politiques pour les nouvelles tables (propriété via auth.uid())
Sécurité : Aucun secret, jeton GitHub ou clé Supabase n'a été enregistré dans le code source, les logs ou les fichiers publics. Le fichier .env.example ne contient aucune valeur réelle.
